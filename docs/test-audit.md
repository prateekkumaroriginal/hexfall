Test audit, 7 October 2026

Follow-up cleanup: the earlier five-joint orc model, exports, decoder, tests, and authoring scripts have been removed. The renderer no longer accepts that model. Its crowd test now checks slime batching; the existing rigged-orc tests cover the current orc. Exact leg-proportion and eye-size tests, polygon lower bounds, exact asset counts, and filename/source-text assertions have been removed. Required clips/morphs and the upper polygon budget remain. Three browser scripts now use the application's parsed default settings, the Chrome script opens Status check, and the benchmark waits for the rigged asset. The inventory below records the pre-cleanup audit and its original recommendations; links to removed files are historical. Follow-up verification passed 114 tests across 13 files, lint, and the production build. The build still reports its existing large-chunk warning. Browser preview opened but subsequent inspection and navigation timed out, so visual verification and full browser-script execution remain unverified.

The suite is mostly useful. I would keep the gameplay, collision, settings-boundary, animation, and resource-lifecycle coverage. There is avoidable maintenance in exact art specifications, repeated balance numbers, and tests for the retired orc export. Stronger TypeScript would improve the code and test fixtures, but would replace very little of the behavior currently tested.

I reviewed all 14 test files, all five browser check scripts, and the corresponding implementation and configuration. At commit `56d25c9`, `pnpm test` passed all 118 expanded cases in 26.75 seconds. `pnpm exec tsc --noEmit --incremental false` also passed. Parameterized cases count separately, so 118 does not mean 118 independently written test scenarios. Browser scripts were inspected, not executed. No coverage or mutation score was measured. Passing tests do not establish that every assertion would catch its intended regression.

This report changes no application code or tests. Recommendations below are based on the current implementation, rather than an assumption that every historical regression remains a permanent requirement.

The clearest waste is at assertion level, rather than whole-file level. I would remove `ORC_MODEL_URL` containing `rigged`, and the check that `onBeforeCompile.toString()` does not contain `orcDeform`. A filename fragment and the absence of a source-code word do not establish correct rendering. The geometry checks already provide more meaningful evidence.

The current orc test also requires more than 119,000 triangles, later more than 119,900, while limiting the asset to 120,000. Those lower bounds obstruct a legitimate mesh optimization. If they exist to prevent accidental geometry loss, check the affected socket geometry or approved asset metadata explicitly. Retain a maximum triangle budget. Likewise, require the bones and clips the renderer consumes instead of exactly 17 joints and exactly three clips unless those exact totals have a documented reason.

The old export deserves separate treatment. [creature-art.md](creature-art.md) explicitly says the game does not load `orc.glb` or `orc-blender-data.json`. Code references agree: `buildBlenderOrcGeometries` is consumed by tests, while the engine loads the rigged GLB. The two old-export tests and the legacy half of the crowd test support an archival authoring path, not the shipped gameplay path. That is a valid optional asset workflow, but a weak default application gate.

Exact balance numbers are not automatically slop. Two-hit slimes and four-hit orcs are documented game rules. Preserve a small number of explicit acceptance examples for those rules. Avoid repeating the same health values both through config imports and literals in the same test. The five wave-speed cases duplicate the same linear equations with hardcoded coefficients; first/last supported waves plus the changed-config scenario would provide a smaller, defensible set. That is a coverage tradeoff, not a TypeScript improvement.

Some tests overstate what they establish. The simulation pause test compares `snapshot()`, which excludes player position and projectile/enemy state. Motion during pause could escape that comparison. The five-wave test sets `remaining = 0` without actually clearing enemies, so it checks empty-wave bookkeeping rather than a full successful run. Keep the bookkeeping test, and strengthen one case to prove that a live enemy blocks progression. The nearest-enemy shot test advances a small distance per step; it does not independently prove nearest-hit ordering when one step crosses multiple enemies.

`chrome-check`, `performance-check`, and `environment-check` construct `Engine` with settings missing `fieldOfView`. The engine passes this missing value into its camera calculation during resize, which yields `NaN`. This conclusion follows directly from the source; the browser symptom was not executed in this audit. These `.mjs` scripts sit outside the TypeScript project's `include`, so the successful typecheck offers no protection here. Their hardcoded localhost URL, installed Chrome/Edge requirement, and lack of package-script integration also make them easy to neglect. There is no checked-in `.github` workflow wiring them into CI.

Better TypeScript would help most in these places:

1. Typecheck browser fixtures. Move scripts to a checked TypeScript setup, or use checked JavaScript with explicit imported types. Build settings fixtures with `satisfies Settings` or a complete shared default. This catches the missing FOV at development time and requires no new runtime test for property presence.
2. Narrow `Enemy.kind` from `number` to `0 | 1`, or named species literals. Use exhaustive species configuration. Existing `Phase` is already a useful union. A legal species type prevents invalid values; it cannot prevent using slime damage for an orc.
3. Derive `RenderScale` from `typeof RENDER_SCALE_SETTINGS.OPTIONS[number]['VALUE']`. Use it in settings and rendering APIs. This prevents typed callers from passing 0.65. Keep every malformed-save test because localStorage JSON is outside the type system.
4. Parse JSON as `unknown`, then narrow it. Introduce a validated orc asset type containing required clips, face/morph information and eye landmarks. Have the loader construct it and the renderer consume it. An asserted `as ValidatedOrcAsset` would not provide that guarantee. Keep loader and binary-asset tests at this boundary.
5. Give creature batches structured or template-literal keys instead of unrestricted `Map<string, ...>` and unchecked `key.split(':') as [Bone, Surface]`. Validate generated JSON once. Types can prevent misspelled authored keys; they cannot prove that packed triangle indices reference real vertices.
6. Replace untyped `Object.assign(enemy, overrides)` fixtures with a helper accepting `Partial<Enemy>` or overrides checked with `satisfies Partial<Enemy>`. `Object.assign` does not require source properties to match the target's property types. Tightening the production type alone would leave this fixture loophole.
7. Adopt checked indexed access incrementally. A non-writing compiler probe with `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes` produced 479 diagnostics, 275 in tests and 204 elsewhere. These are not 479 confirmed bugs; many are array-bound assumptions the compiler cannot infer. Use checked access/helpers and explicit validated tuples where useful, rather than scattering non-null assertions.

I would not introduce elaborate numeric brands or a heap-allocated state-machine representation throughout pooled entities solely to reduce tests. They add complexity while leaving the main risks unchanged. Ordinary TypeScript cannot prove collision geometry, finite numbers, correct damage timing, frame-rate independence, GPU disposal, topology, camera projections or visual quality.

There is no whole current-behavior test file I can justify deleting merely by improving its types. The realistic reduction comes from removing retired behavior and duplicate assertions. Better types should prevent future shape/enum tests and simplify setup. They should not be used as an excuse to remove external-input or numerical-behavior checks.

Recommended order of work:

1. Fix and typecheck the three stale engine fixtures, repair the Chrome report-button navigation, and ensure the benchmark waits for current assets. Otherwise browser evidence is unreliable.
2. Remove the filename/source-string assertions and polygon lower bounds. Move the old export checks out of the default gameplay gate if that authoring workflow is still supported.
3. Retain core gameplay and rendering contracts. Separate current-asset acceptance checks so resculpting does not require pretending a deliberate art change is a gameplay regression. Keep those checks required whenever the relevant asset or rig code changes.
4. Strengthen pause state, live-enemy wave progression, late-load disposal and positive browser-render assertions. Fill the small settings-parser gaps. Prefer these over adding more exact pose coordinates.
5. Introduce narrow species/render-scale types, typed fixtures and validated asset contracts. Consider dependency injection for configuration tests only when editing that subsystem, rather than undertaking a broad rewrite just to remove three module mocks.

I would judge this cleanup by which failures it catches and which harmless changes stop breaking it. A lower test count alone would be a poor success metric. Splitting the oversized renderer tests could even increase the count while making the suite easier to maintain.
